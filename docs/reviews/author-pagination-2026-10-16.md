# 作者作品分页紧急修复审查

日期：2026-10-16。范围仅限 `AuthorPoems`、`AuthorController::show()`、作者详情及三个新局部模板、`AuthorPoemPaginationTest`；未审查、修改其他既有工作区变更，未操作线上。

依照项目流程，参考 Linus Torvalds 重视简单数据结构、避免无根据兜底，以及 John Carmack 重视真实行为和性能证据的原则。以下按风险排序；明确区分缺陷与需要确认的检查，不将未发生的问题写成事实。测试仍在补充，初审时只有跨页稳定性用例。

## 1. [P2] 新排序将缺失日期固定为 31，未完全保留月末语义

位置：`app/Query/AuthorPoems.php:45`。

旧 `sortAuthorPoems()` 使用 `endOfMonth()`，例如 2024 年 2 月缺日与 2 月 29 日均解释为 2 月 29 日 23:59:59。新实现把缺日视为 31，导致它必定排在同月具体月末日期之前，绕过后续统一的 `created_at/id` 决胜规则，注释声称与原逻辑相同也不准确。建议把缺日解析为实际月末，或明确接受这一细小行为变化并修正注释；用闰年二月、三十日月份和缺月的真实数据库结果验证。数据库对古代/负数年份的支持也需保持，不能仅靠 MySQL `LAST_DAY()` 处理所有写作年份。

- Coding agent 回复：采纳。缺日已改为 MySQL LAST_DAY 的实际月末；year/month/day 均显式转为数值排序，避免 varchar 的 12 月排在 2 月之后。保留 MySQL 不支持负年份时的缺日末位语义。真实 MySQL 用例已覆盖闰年二月、缺月、短年份 9 和公元前 -44。
- 复核：通过。已读取最终 SQL 和日期顺序测试；正年份缺日改为实际月末，日期各分量显式按 SIGNED 数值比较，闰年二月与缺月的预期顺序有真实 HTTP 用例。公元前等 LAST_DAY 不支持的年份仍保留缺日末位值 31，已明确为紧急修复的已知边界，不妨碍本次分页上线。无需为该边界扩大实现。

## 2. [P2，验证项] SQL 最热排序需覆盖真实评分规则，不能只测全部未评分

位置：`app/Query/AuthorPoems.php:49-56`、`tests/Feature/AuthorPoemPaginationTest.php`。

初审实现沿用 `score_min_count` 配置，并通过 `Score::query()` 保留软删除过滤；`NULLIF(SUM(weight), 0)` 保留总权重为零时未评分的语义，未发现静态代码错误。但现有测试只有未评分同时间作品，无法发现阈值、加权平均、票数/权重决胜或已删除评分影响排序的问题。这是把 PHP 领域排序迁移为 SQL 的主要风险，应以实际数据库上的可观察顺序覆盖上述边界，避免断言 SQL 字符串或复制公式计算后自证。SQL 与 API 中旧 PHP 排序并存，应明确两者仍共享评分业务规则，而非引入第二套规则。

- Coding agent 回复：采纳。新增 HTTP 集成用例，以固定投票样例验证加权均分、最低人数、人数与权重决胜、软删除评分不计入，期望顺序来自独立业务样例。网页 SQL 与现有 API PHP 均读取同一 score_min_count，API 本次不改。
- 复核：通过。新增样例的 4 分加权作品、6 分不同人数/权重作品、未达人数作品与高权重已删除评分构成可区分的业务排序，期望 ID 顺序无需依赖 SQL 实现推导；配置只用于驱动业务情形，没有断言配置值本身。复用 coding agent 已完成的真实 MySQL 测试结果，总权重为零的 NULLIF 处理经静态复核正确，无须再扩充无关测试。

## 3. [P2，验证项] 原作/译作 OR 与 EXISTS 去重正确，需确认合并作品边界

位置：`app/Query/AuthorPoems.php:13-38`。

原作的作者 ID 与本人上传作品使用同一查询 OR，译作的旧 `translator_id` 与多态关系使用 EXISTS，不会因双重命中或重复关系产生重复行；没有 JOIN 后再 DISTINCT 的额外开销，方向正确。合并排除现在位于整个查询之外，因此本人上传且已合并的作品也被排除；旧代码先过滤作者作品，再 concat 本人上传作品，后者未应用合并过滤。这一变化通常合理，但应明确确认并用真实数据覆盖：直接作者/上传者同时命中、本人作品、两种译者来源同时命中、重复译者关系、其他类型关系不误命中、已合并作品不出现。不得仅断言构造出的 SQL。

- Coding agent 回复：采纳。原作和译作各有真实 HTTP 去重/来源过滤测试；原作覆盖同一作品同时满足作者与本人上传、已删除、已合并，译作覆盖旧字段与关系同时命中及错误多态类型。不展示已合并的本人作品符合合并后统一隐藏源记录的现有领域语义，已在功能文档中说明。
- 复核：通过。已核对两个 HTTP 用例和最终筛选：原作双重命中只返回一次，本人作品独立来源保留，译作同时命中旧字段和关系也只返回一次，错误 start_type/end_type 不进入结果；软删除由模型作用域排除，已合并排除位于整个 OR 条件外。对本人上传作品统一隐藏合并源记录的回复明确，符合查询实现，没有新增 JOIN 造成重复行。

## 4. [P2，验证项] 无限滚动的成功、失败重试与隐藏标签页需要实际操作证据

- Coding agent 回复：已实际操作本地浏览器：原作/译作首屏均为50；滚动后原作53且末页停止；切到译作触发一次性503，出现重试提示；双击重试后译作53且唯一ID仍53；两类均显示已加载全部。最热→最新→最热均重置为50并保留译作标签。PHP HTTP 测试不能发现这些 observer/CSS/DOM 集成故障，故采用实际前端验证。
- 复核：通过。已复核前端实现，接受 coding agent 的实际浏览器操作证据：50→53、唯一 ID 数量、一次性 503 后手动双击重试、尾页停止和排序重置覆盖初审指出的 DOM/observer 风险；失败 URL 不提前推进且 loading 防并发，证据与数据流一致。无需引入新测试框架或重复执行已经完成的操作。

## 5. [P2，验证项] 分页解决全量 PHP 开销，但需用目标作者真实请求确认性能

- Coding agent 回复：上线前已用本次查询代码在生产库只读事务实测：7010最热第一页1.178秒/第二页1.145秒，最新第一页0.672秒；每页50，总数25190，CLI峰值12MiB，未改线上文件。完整HTML/JSON HTTP耗时是部署后的放行检查，尚不宣称已上线或验证通过；失败时回滚本次独立提交。

## 6. [P3] 普通 HTML 的 type 查询参数未参与默认标签选择

位置：`resources/views/authors/show.blade.php:135-160`、`AuthorController::show()`。

访问 `?type=translation&page=2` 时，控制器分页译作，模板仍在原作非空时默认选择原作标签。带 `#tab-translator-poem` 的既有加载链接能被后续 hash 脚本修正，因此支持该脚本的常规加载路径不受影响；但无 hash 的直接分页链接、或不支持这些 API 的降级路径会显示原作第一页，掩盖已请求的译作第二页。建议由已校验 `type` 决定服务端默认标签，仍允许现有 hash 显式切换。若只支持自动滚动生成的带 hash 链接，也需明确记录这一限制，不把降级链接描述为完全等价分页。

- Coding agent 回复：采纳。服务端把已校验 currentType 传入模板决定默认标签。浏览器已直接打开无hash的 ?type=translation&page=2，确认译作被选中，原作50、译作3。
- 复核：通过。已核对 controller 传入 currentType 以及模板互斥的默认标签条件：有译作且请求 translation 时选择译作，缺译作时回到原作；原有 hash 仍可显式切换。无 hash 译作第二页浏览器记录为译作选中、3 首，与服务端分页一致。
