# r13：活动列表查询与缓存审查

范围：尚未暂存的 CampaignRepository、CampaignAPIController 及 CampaignIndexApiTest。没有独立规格，依据改动推断目标为消除空缓存阻挡外部新增活动、在分页前过滤测试活动。本轮静态审查，没有运行测试。按影响排序；前四项为应处理问题，后两项为非阻塞观察。

## 1. [P1] 旧的非空缓存仍可能保留约 92 小时

位置：`app/Repositories/CampaignRepository.php:61-67`。

缓存 key 和 tag 沿用旧值，旧实现 TTL 为 `4600 * 72` 秒。新代码看到非空值直接返回，所以新增的 180 秒 TTL 只影响以后写入的缓存，无法缩短已存在缓存。上线时已有列表漏掉外部新增活动的情况可以继续持续数天。需要发布时清理 tag，或切换缓存版本；并验证迁移行为。

## 2. [P2] JSON 显式 null 的可见性发生变化

位置：`app/Repositories/CampaignRepository.php:56`。

旧 PHP 判断用 `isset(settings['test']) && settings['test']`，因此 `{"test": null}` 属于可见记录。JSON 提取的 JSON null 不等于 SQL NULL，也不等于 JSON 数字 0，新 SQL 条件将该记录过滤。需要确认 test 字段的合法形态，保留旧可见性或明确规范；至少以真实 MySQL 边界测试验证 null / 缺失 / 0 / false / 1，不能只测试缺失与 1。

## 3. [P2] 数据库分页缺少唯一排序决胜条件

位置：`app/Repositories/CampaignRepository.php:57,70-73`。

仅按 start 排序，多个活动开始时间相同时，LIMIT/OFFSET 查询不保证相对顺序，连续页可能重复或遗漏。旧实现每个请求也独立执行全量查询，原本就没有跨请求稳定性保证；改成数据库分页后，不同 LIMIT/OFFSET 的执行计划也可能改变同时间记录的顺序。本项为应补强的既有风险，并非此次新增缺陷。增加 id 的稳定决胜顺序，并通过跨页结果验证。

## 4. [P2] “详情清空旧空缓存”测试无法发现其目标分支失效

位置：`tests/APIs/CampaignIndexApiTest.php:56-66`。

即使删除 controller 新增的清缓存调用，下一次 index 仍会因为 repository 主动绕过空缓存而返回该活动，所以此测试仍通过。若缓存失效确为必要契约，应直接在详情访问后检查缓存公共边界；否则删掉冗余的 controller 改动及这个专属测试，保留 index 对旧空缓存恢复的行为测试。

## 5. [观察] 空结果不缓存是负载上的明确取舍

位置：`app/Repositories/CampaignRepository.php:83`。

所有空页每次都会访问数据库，包括超过末页的请求。该行为直接服务于立即发现外部新增数据，不能单凭这一点当作缺陷；建议说明取舍并保留当前简洁实现，只有出现实测负载后再考虑短负缓存。180 秒 TTL 的业务依据也应在需求或注释中说明，无需写常量值断言。

## 6. [观察] 可见性规则尚未成为单一来源

位置：`CampaignRepository::visibleCampaignQuery` 与 `CampaignAPIController::list/show`。

仓库和 list 各有一份 SQL 可见性条件，show 又保留 PHP truthiness 判断，第二项已说明差异风险。目前无需为抽象而引入额外层；若修正合法值语义，可考虑用 Campaign scope 统一列表规则，并明确详情是否允许测试活动访问。allInUse 当前没有项目调用方，未发现因新增过滤直接破坏现有调用的证据。
